Build in parallel. Verified.

A BuildKit frontend for container images. You say which steps are independent; every build checks that they are, runs them at the same time and caches them one by one.

  • any base image
  • plain BuildKit
  • three commands
  • works without the rest of nomira
Frontend docs Source on GitHub

Early stage of development (alpha): the recipe schema may still change.

What changes when one step changes

The same build twice. In both, the step config b was edited.

Containerfile: a chain

Every step builds on the one before. Everything after the change runs again.

  1. packages from cache
  2. config a from cache
  3. config b changed, rebuilt
  4. config c rebuilt
  5. finish rebuilt

nomira: phases and groups

Groups of a phase start from the same state. Siblings of the changed group stay cached.

  1. phase packages from cache
  2. phase configs: three groups, in parallel
    • group a from cache
    • group b changed, rebuilt
    • group c from cache
  3. check and merge runs again, cheap
  4. phase finish rebuilt

How it works

  • Phases

    Run one after another, in the order you write them.

  • Groups

    Independent parts of a phase. They run at the same time, and each has its own cache entry.

  • Check

    Every build records which files each group wrote or deleted. If two groups overlap, the build aborts before anything is merged.

  • Merge

    The results of the groups become layers of the image. The next phase starts from their sum.

A recipe, and a conflict

One line at the top selects the frontend. Any BuildKit can then build the file.

recipe.yml

# syntax=ghcr.io/nomira-os/nomira:1-alpha
settings:
  base: docker.io/library/alpine:3.22
phases:
  - name: content
    groups:
      a: ["run echo a > /etc/a"]
      b: ["run echo b > /etc/b"]

If both groups write /etc/a

phase "content": declared-independent
groups are not disjoint (policy: strict):
  groups "a" and "b": /etc/a (both write)

Where it fits, and where it does not

  • Good fit

    Builds with many parts that have nothing to do with each other, such as the configuration of a whole operating system.

  • Little gain

    Short builds, or builds where every step needs the one before. A Containerfile does that just as well.

  • Not declarative

    A recipe lists commands that run in order. The frontend adds structure and the check, not a new language.

  • Tried so far

    With buildctl, on Alpine and Arch images. Other BuildKit clients such as docker buildx should work but are untested.

Continue with using the frontend on its own or the recipe schema.
